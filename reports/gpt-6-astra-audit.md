### 1. Medium — Redirected Google sign-in rejects every local second-factor challenge

- **Location:** `lib/auth/oauth.ts:332` (`oauth.googleCallback` challenge delivery), `lib/auth/oauth.ts:439` (`oauthResult`); `lib/auth/two-factor-challenge.ts:685` (`issueTwoFactorChallenge`).
- **Evidence and failure scenario:** A Google sign-in with `callbackURL` for an account requiring local 2FA stores the challenge body through `completeResponse`. That body has `twoFactorRedirect`, `twoFactorMethods`, `twoFactorOptions`, and `defaultMethod`, but no `success` property. `GET /api/auth/oauth/result` consumes both verification records and then rejects every body without `success === true`. Consequently the documented redirect flow in `docs/oauth-sign-in.md:61` returns 401 instead of the offered second-factor options, and retrying cannot retrieve the consumed result. Direct JSON delivery and sign-ins that do not require local 2FA take different branches and escape the defect.
- **Impact:** Google sign-in through the documented callback page fails for accounts requiring local 2FA. No authentication bypass is involved.
- **Remediation:** Define and validate the complete OAuth outcome union at storage and retrieval, admitting the existing challenge contract as well as the successful session envelope. Add coverage for `callbackURL` combined with local 2FA; existing tests exercise those dimensions separately.
- **Verification:** `bun --no-env-file "$env:TEMP/codex-auth-audit.ts"` provisioned an isolated test database and exercised the routed OAuth, TOTP, and backup-code scenarios reported here. ### 2. Medium — Factor enrollment commits without revalidating the credential it activates

- **Location:** `lib/auth/two-factor-enrolment.ts:302` (`confirmTotpEnrolment` read and verification), line 330 (credential update), line 249 (`startTotpEnrolment` replacement), line 890 (`recordPasskeyEnrolment`), and line 722 (`deletePasskey` last-factor guard); `lib/auth/two-factor.ts:245` (registration after-hook).
- **Evidence and failure scenario:** Confirmation reads secret A and verifies its code before acquiring the user lock. A concurrent setup request can replace that unverified credential's secret with B. Confirmation subsequently acquires the lock and sets `verified: true` using only the unchanged credential ID. It then enables the factor and revokes other sessions. A routed reproduction against a disposable test database paused confirmation at the transaction boundary, completed the second setup, and resumed confirmation: `{"scenario":"TOTP confirm A after start B","startA":200,"startB":200,"confirmA":200,"secretReplaced":true,"unprovenSecretVerified":true}`.
- **Additional occurrence:** Passkey registration in installed `@better-auth/passkey` 1.7.3 persists the credential before the local enrollment hook. Another request can list and delete that credential before the hook acquires the user lock. Deletion permits this because passkey method intent does not yet exist. The hook then records intent and enables 2FA without rereading any credential. A routed reproduction using a valid synthetic WebAuthn registration, two independent grants, and the actual list/delete routes returned registration and deletion status 200, `"remainingPasskeys":0,"twoFactorEnabled":true,"intent":["passkey"],"offeredMethods":[],"nextSignInStatus":403`, with next-sign-in error code `TWO_FACTOR_UNAVAILABLE`.
- **Impact:** Overlapping setup attempts can activate an authenticator the user has not successfully configured or remove the only usable factor before it is activated. A user who scanned TOTP secret A is told setup succeeded but cannot authenticate after the account switches to B. Concurrent `/two-factor/disable` can also delete the TOTP credential: confirmation's update affects zero rows, but it still writes method intent and enables 2FA. The passkey reproduction proves a subsequent sign-in fails. The reach is bounded to concurrent factor management for the same account; the initiating session remains available for recovery.
- **Remediation:** Under the user lock, revalidate the exact credential being activated: compare the TOTP secret/version and unverified state, and check the registered passkey's ID and owner. Require a successful current-credential check/update before changing intent, the user flag, or sessions. Surface failed passkey finalization to the registration caller instead of merely logging it. Cover replacement/deletion between proof or persistence and activation; the existing successful-enrollment and last-passkey-removal tests pass but do not exercise these interleavings.
- **Verification:** `bun --no-env-file "$env:TEMP/codex-auth-passkey-audit.ts"` ran the isolated routed passkey reproduction and the existing focused checks. Its test command was `bun test --no-env-file --preload ./tests/helpers/preload-database.ts '--test-name-pattern=accepts an authenticator that did|the last passkey of a passkey-only account is refused' tests/integration/two-factor-passkey.test.ts`: 2 passed, 15 filtered, 0 failed, 15 assertions. The harness paused the enrollment transaction only after the credential became visible and restored the transaction wrapper before calling list/delete.
- **TOTP coverage:** The isolated auth harness from finding 1 ran `bun test --no-env-file --preload ./tests/helpers/preload-database.ts '--test-name-pattern=flips the flag and records the intent row the challenge reads' tests/integration/two-factor-totp.test.ts`: 1 passed, 0 failed, 2 assertions.

### 3. Low — The default page size exceeds an explicitly supplied maximum

- **Location:** `lib/data-table/parsers.ts:354` (`parseSearchParams`), `db/queries/data-table.ts:87` (`parseDataTableParams`).
- **Evidence and failure scenario:** `maxPerPage` constrains a supplied `perPage`, but an omitted `perPage` receives an unconditional fallback of 10. The query builder clamps only to the global maximum. Calling the actual shared query parser with `maxPerPage=1` produced `{"perPage":10,"limit":10,"offset":0}`; adding `&perPage=1` produced `{"perPage":1,"limit":1,"offset":0}`. Users, permissions, and media list endpoints share this parser.
- **Impact:** A valid request that supplies a maximum below 10 receives a larger page than requested. The global ceiling still applies; this is a bounded pagination contract defect.
- **Remediation:** Bound the default page size by the parsed `maxPerPage`. Existing parser tests cover absent parameters and over-cap supplied values separately; add their combination with a maximum below the default.

### 4. Medium — Nightly retention can delete a freshly resent, unexpired OTP

- **Location:** `db/maintenance.ts:230` (`sweepVerificationSessions`), `utils/otp.ts:692` (`processOtpSend` session upsert).
- **Evidence and failure scenario:** Retention removes an unconsumed verification session once its original `createdAt` is older than one day, cascading deletion to its code. Resending reuses that session and updates `lastSentAt` and the code's `expiresAt`, but preserves `createdAt`. A user can abandon a verification attempt, return more than a day later just before the nightly sweep, and receive a fresh code that the sweep immediately deletes while it is still valid. The shared sender serves contact verification/change, passwordless sign-in, recovery, and second-factor OTP flows.
- **Impact:** Those users cannot complete verification with a newly delivered valid code and must request another. This is reachable during ordinary use around the scheduled sweep; it does not depend on high traffic.
- **Remediation:** Determine abandonment from current activity and proof validity, preserving freshly renewed sessions/codes. Coordinate deletion with the send transaction so a candidate cannot become active before deletion. The existing focused retention test passes but compares old stale rows with freshly created rows; it does not cover an old session with a recently refreshed code.
- **Verification:** `bun tests/helpers/run.ts integration retention-sweep.test.ts '--test-name-pattern=a proof row past its TTL is removed'`: 1 passed, 18 filtered, 0 failed, 2 assertions.

### 5. Low — SQLite statement tracking preserves a workaround superseded by the pinned Bun runtime

- **Location:** `lib/sqlite/driver.ts:136` (`openConnection` statement registry), `lib/sqlite/driver.ts:181` (`close`).
- **Evidence:** The adapter retains every prepared statement in a `Set`, tracks separate finalization state, and manually finalizes the set before calling `db.close(true)`. Bun 1.4 introduced finalization of all outstanding statements by `close(true)` itself. Installed Bun 1.4.2 and `node_modules/bun-types/sqlite.d.ts:274` confirm this contract. A focused in-memory check preparing both an uncached statement and a cached query, calling only `db.close(true)`, and then reading each produced `prepared Database has closed` and `cached Database has closed`; calling each statement's `finalize()` afterward also succeeded. [Bun 1.4 release notes](https://bun.com/blog/bun-v1.4).
- **Impact:** The registry and parallel lifecycle bookkeeping add maintenance cost without providing the stated leak prevention on the supported runtime. The comment justifies them using `close(false)`, which this adapter does not call. No current leak or measured performance regression is claimed.
- **Remediation:** Keep the portable adapter and explicit finalization for short-lived statements, but delegate connection-wide finalization to `db.close(true)` and remove the redundant registry/state. Preserve deterministic close semantics if another driver is introduced.

### 6. Medium — A successfully used TOTP remains usable for another authentication

- **Location:** `lib/auth/two-factor.ts:188` (`verifyTOTP` wrapper), `lib/auth/recovery-second-factor.ts:40` (`verifyRecoveryTotp`).
- **Evidence and failure scenario:** Sign-in delegates to the installed Better Auth 1.7.3 verifier, which validates the time-based code without reserving its credential/time step. The local recovery verifier likewise only compares the code. The user lock serializes sign-in requests, but no persistent replay state changes between them. A routed reproduction completed two distinct password challenges with the same TOTP and returned `{"scenario":"Reuse same TOTP across distinct password challenges","completionStatuses":[200,200]}`. Challenge tokens themselves were different and correctly consumed. RFC 6238 requires rejecting reuse after successful validation. [RFC 6238 §5.2](https://www.rfc-editor.org/rfc/rfc6238.html#section-5.2).
- **Impact:** An attacker who knows the password and obtains a recently used authenticator code can still open another session during its acceptance window. The window and required first factor bound the exposure; successful use by the owner does not spend the code.
- **Remediation:** Atomically reserve each accepted credential-generation/time-step combination in shared durable state across sign-in and recovery. Preserve the configured clock tolerance. Existing TOTP tests cover successful sign-in and challenge consumption, but not reuse across fresh challenges or verification paths.
- **Verification:** The isolated auth harness from finding 1 ran `bun test --no-env-file --preload ./tests/helpers/preload-database.ts '--test-name-pattern=the challenge cookie plus a correct code completes the sign-in' tests/integration/two-factor-totp.test.ts`: 1 passed, 0 failed, 3 assertions, before reproducing reuse across two fresh challenges.

### 7. Medium — Stale visibility cleanup can delete the only live copy of a file

- **Location:** `lib/media/visibility.ts:86` (`tryDelete` eligibility read), `lib/media/visibility.ts:100` (object deletion), `lib/media/visibility.ts:233` (`transitionFile` flip), `lib/media/visibility.ts:303` (`retryTransitions`).
- **Evidence and failure scenario:** Cleanup checks the row's current bucket, then deletes from object storage without coordinating that destructive operation with the visibility flip. A publish stalled past the ten-minute transition threshold can overlap the sweep: the sweep reads the still-private row and starts deleting the public target; publish resumes, flips the row to public, and deletes the private source; the sweep's previously authorized public deletion finishes afterward. The R2 client has no configured request deadline that prevents this overlap. A focused reproduction using the production lifecycle functions, a disposable PostgreSQL database, and the existing object-store stub finished with `{"bucketType":"public","transition":null,"public":false,"private":false}`.
- **Impact:** Both copies of one affected file are lost while its database row appears active and settled. This needs an unusually stalled transition overlapping recovery, so its reach is bounded. It is possible within one process and also across workers.
- **Remediation:** Give each transition/recovery operation an identity and coordinate destructive cleanup with the right to flip the file, so a bucket cannot become authoritative while an older deletion of its object is outstanding. A marker comparison or another unlocked read alone cannot fence an external delete. Keep object-store I/O outside ordinary short database transactions. The existing marker-takeover test passes but starts old cleanup after the new publish; it misses deletion already in flight.
- **Verification:** `bun --no-env-file --tsconfig-override ./tsconfig.json "$env:TEMP/codex-media-audit-repro.ts"` ran the isolated production-function races in findings 7 and 8. Existing check `bun tests/helpers/run.ts integration media-files --test-name-pattern='a publish that lost its marker to a second publish never deletes the live object'`: 1 passed, 34 filtered, 0 failed.

### 8. Medium — Recursive folder deletion removes a file successfully moved outside the subtree

- **Location:** `lib/media/lifecycle.ts:369` (`deleteFolderTree` committed plan), `lib/media/lifecycle.ts:375` (subsequent `deleteFiles` call), `lib/media/lifecycle.ts:218` (`deleteFiles` selection); `lib/media/files.ts:182` (`moveFiles`).
- **Evidence and failure scenario:** Recursive deletion commits its subtree/file-ID plan before marking those files as deleting. A concurrent move can commit in that gap. Deletion then locks the planned IDs without checking their current folder membership and removes their rows and objects. The later subtree check occurs after object deletion and does not detect a file moved out. A production-function reproduction committed a move into an unrelated folder between planning and marking; recursive deletion returned one deleted folder and that file's ID, with `"movedFileExists":false,"movedObjectExists":false`.
- **Impact:** Concurrent library organization can lose a file outside the requested deletion subtree even though its move succeeded. The impact is limited to the overlapping folder/file operations.
- **Remediation:** Resolve/revalidate the subtree and mark its files as deleting in the same transaction, coordinating file locks with move operations. Reuse the shared deletion marking logic, then perform object cleanup after commit. The existing recursive-deletion test passes but does not interleave a move between planning and marking.
- **Verification:** `bun tests/helpers/run.ts integration media-files --test-name-pattern='the subtree goes in one request'`: 1 passed, 34 filtered, 0 failed, 16 assertions. The isolated reproduction command is recorded in finding 7.

### 9. Medium — Backup-code acknowledgement can activate a different set from the one saved

- **Location:** `lib/auth/two-factor-enrolment.ts:449` (`generateBackupCodes` response), `lib/auth/two-factor-enrolment.ts:479` (`acknowledgeBackupCodes`).
- **Evidence and failure scenario:** Generation returns codes without their version. Acknowledgement accepts no set identity and marks whichever version currently exists as acknowledged. Reject stale acknowledgements. Existing acknowledgement tests pass but cover only the current generation.
- **Verification:** The isolated auth harness from finding 1 ran `bun test --no-env-file --preload ./tests/helpers/preload-database.ts '--test-name-pattern=are not a usable method until the user acknowledges them' tests/integration/two-factor-management.test.ts`: 1 passed, 0 failed, 8 assertions, before reproducing acknowledgement of the replacement generation.

### 19. Low — The SQLite benchmark incorrectly concludes that denied requests avoid writer contention

- **Location:** `bench/sqlite/FINAL-REPORT.md:162` and line 171 (refusal-path interpretation), `bench/sqlite/shared/schema.mjs:83` (`SQL_RL_CONSUME` explanation).
- **Evidence:** The benchmark describes an exhausted-key UPSERT as a primary-key read that does not contend because it changes no rows. A focused two-connection WAL check on Bun 1.4.2 / SQLite 3.53.2 showed otherwise: without a competing writer the production denial returned `null`; while another connection held `BEGIN IMMEDIATE`, a plain SELECT returned `{"count":1}`, but both benchmark and production denial statements returned `{"code":"SQLITE_BUSY","message":"database is locked"}`. SQLite starts a write transaction for INSERT, including an UPSERT whose condition makes its update a no-op. [SQLite transactions §2.1](https://sqlite.org/lang_transaction.html#read_transactions_versus_write_transactions), [SQLite UPSERT](https://sqlite.org/lang_upsert.html).
- **Impact:** The written conclusion overstates the denial path's concurrency benefit. No changed rows or WAL growth proves reduced mutation, not freedom from writer serialization; relying on that interpretation misreads the benchmark's capacity evidence. This corrects the benchmark interpretation rather than re-reporting the already documented multi-writer deployment restriction.
- **Remediation:** Describe the path as avoiding row mutation while retaining writer contention, and include a held-writer denial check when validating this benchmark conclusion. The existing command `bun tests/helpers/run.ts unit sqlite-semantics --test-name-pattern='denied requests perform zero writes'` passed one test with two assertions; it checks changed rows rather than competing-writer behavior.
