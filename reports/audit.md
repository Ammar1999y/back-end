## Findings

### Medium — SVG sanitization leaves external references on elements other than `image` and `use`

- **Location:** `utils/images/svg-optimizer.ts:201` (`sanitizeSvg` reference-attribute guard), `lib/r2/upload-helper.ts:213` (`processImage` SVG branch), and `lib/r2/upload-helper.ts:324` (`uploadImagesToR2` public upload)
- **Evidence:** `sanitizeSvg` constrains `href` and `xlink:href` only when the element is `image` or `use`; the generic value check does not reject an ordinary `https:` value. The upload path accepts `image/svg+xml`, sanitizes and optimizes it, then stores it in the public bucket with `Content-Type: image/svg+xml` and an inline disposition. On Bun 1.4.0, `bun -e '<focused sanitizer probe>'` returned `isValid: true` and preserved `<feImage href="https://attacker.invalid/pixel.png"/>` in both `cleanedSvg` and the final SVGO output; an external `mpath` survived as well. The existing external-reference tests cover `image`, `use`, and CSS URLs but not other SVG URL-bearing elements. SVG 2 defines `feImage` as an external-resource reference, and top-level SVG documents use dynamic interactive processing, where external references are permitted: https://www.w3.org/TR/SVG/linking.html and https://www.w3.org/TR/svg-integration/.
- **Impact:** An authorized uploader can store an SVG that appears self-contained during review but makes a request to an attacker-controlled URL when someone opens the public object directly. That discloses the viewer's IP and request metadata and lets the visible image depend on remotely mutable content. For example, `<filter><feImage href="https://attacker.example/pixel"/></filter>` currently survives the complete storage transformation.
- **Remediation:** Apply the local-fragment/data-image allowlist to every SVG element and attribute capable of resolving a URL, or remove unsupported URL-bearing/animation/filter elements with a positive SVG allowlist. Validate the post-SVGO document as well, and add end-to-end cases for at least `feImage`, `mpath`, `textPath`, gradients/patterns, animation targets, and both `href` spellings.

### Low — A legal zero-length RIFF chunk hides an animated WebP from the admission check

- **Location:** `lib/r2/upload-helper.ts:81` (`isAnimatedWebp`)
- **Evidence:** The chunk walk returns `false` at `lib/r2/upload-helper.ts:91` whenever `size <= 0`, instead of advancing past the eight-byte header. `tests/unit/upload-validation.test.ts:1167` records this as `test.failing`. A focused Bun 1.4.0 reproduction placed an empty `XMP ` chunk before an animation-flagged `VP8X`; it printed `{"validation":{"valid":true}}`, after which `optimizeImage` rejected the same bytes as a generic `CustomError` with status 422 and the “corrupt or incomplete” message.
- **Impact:** A standards-valid animated WebP can bypass the route's explicit animation rejection. The upload still fails closed in the decoder, but the caller receives the wrong diagnosis after unnecessary decode work instead of the intended animation-specific 400 response.
- **Remediation:** Treat a zero-length chunk as an empty chunk and advance by its eight-byte header; reject only malformed bounds/overflow. Convert the existing expected-failure case into a passing regression test and assert the route-level animation response.

### Low — Better Auth methods are documented and advertised per prefix instead of per endpoint

- **Location:** `routes.ts:326` (`ROUTE_PREFIXES`), `lib/http/route-manifest.ts:227` (`createRouteLookup`), and `lib/http/openapi.ts:468` (`openApiDocument` Better Auth loop)
- **Evidence:** The prefix model assigns `GET` and `POST` to every allowlisted Better Auth path, and the OpenAPI builder unconditionally emits both operations. In installed `better-auth@1.7.1`, `/sign-out` and `/sign-in/email` declare only `POST`; the local passwordless endpoint also declares only `POST` and validates `verifyOtpSchema` at `lib/auth/passwordless.ts:42-87`. Official Better Auth documentation likewise specifies `POST /sign-out` and `POST /sign-in/email`. A temporary integration probe (removed after the run) printed `{"runtime":{"/sign-out":404,"/sign-in/email":400,"/passwordless/verify":404},"documented":{"/sign-out":["get","post"],"/sign-in/email":["get","post"],"/passwordless/verify":["get","post"]}}` for `GET` requests. The same over-broad map makes the 405 boundary include `GET` in `Allow` for POST-only auth paths. Separately, `BETTER_AUTH_BODIES` contains only `/sign-in/email`, so the documented passwordless POST omits its required request body; no OpenAPI test covers that path.
- **Impact:** The published contract tells generated clients that three invalid GET operations are supported and that passwordless verification needs no body. Those requests then return unrelated 400/404 validation responses, and `GET /sign-in/email` reaches Better Auth's captcha processing before method rejection. Capability discovery through `Allow` is wrong for the same paths.
- **Remediation:** Store methods and request schemas alongside each allowlisted auth sub-path, derive Elysia registrations, route lookup, limiter admission, and OpenAPI operations from that one per-endpoint table, and add runtime-versus-document method/body tests for every allowed path. Better Auth's official Elysia integration can generate the dependency-owned portion of the schema, but that framework coupling should remain limited to the already Better-Auth-specific prefix.

### Medium — Production accepts enabled OTP channels with invalid names or missing provider credentials

- **Location:** `utils/validation/otp.ts:54-76` (enabled-channel parsing), `lib/env.server.ts:15-43` and `lib/env.server.ts:106-131` (production startup validation), and `utils/otp.ts:25-45`, `utils/otp.ts:139-180` (provider configuration reads)
- **Evidence:** Channel parsing silently filters unknown values and treats the resulting empty set as an intentionally disabled feature. The production environment guard validates the OTP HMAC key but neither validates channel names nor conditionally requires the selected delivery provider's credentials. A Bun 1.4.0 subprocess with every declared production requirement satisfied, `NEXT_PUBLIC_ENABLED_OTP_CHANNELS=email`, and no `SMTP_USER`/`SMTP_PASS` printed `{"bootChecksAccepted":true,"otpEnabled":true,"smtpUser":null,"smtpPass":null}`. Repeating it with the typo `emial` logged the disabled notice but still printed `{"bootChecksAccepted":true,"otpEnabled":false,"configured":"emial"}`. No startup test covers provider/channel coherence; the deployment guide lists those credentials only as feature-dependent.
- **Impact:** A typo or omitted secret produces a deploy that starts and passes storage readiness but has no usable recovery or passwordless channel. With `email` enabled and SMTP unset, requests are admitted and persisted before delivery fails; with a misspelled channel, every send and verify endpoint answers 404. If email verification is later required for login, the same mistake can lock all newly unverified users out until the deployment is corrected.
- **Remediation:** Parse the channel variable strictly during server startup, reject unknown/duplicate/empty entries, and require the complete credential set for each enabled provider (including a usable sender for email). Add isolated production-startup tests for every channel, missing partial credentials, misspellings, and intentionally disabled OTP.

### Medium — Three application guards block the multi-process mode SQLite was chosen to support

- **Location:** `server.ts:217-218` (`acquireWriterLock` at startup), `lib/sqlite/writer-lock.ts:13-49` (`acquireWriterLock`), `app.ts:237-248` (Elysia `serve.reusePort: false`), and `server.ts:279` / `lib/schedule.ts:80-106` (in-process maintenance ownership)
- **Evidence:** **SQLite is not the constraint, and an earlier version of this finding was wrong to imply it was.** Re-measured on Bun 1.4.0 / SQLite 3.53.2 on Windows, driving the application's own `openDatabase({ durability: 'process-crash-safe' })` and the real `SQL_CONSUME` upsert from eight separate Bun processes against one shared file, 300 writes each on a single contended key: `{"successfulWrites":2400,"storedCounter":2400,"lostUpdates":0,"busyErrors":0,"otherErrors":0}` — twice, including a cold open where all eight processes create and migrate the file simultaneously, and again with the file pre-created. The `SQLITE_BUSY at PRAGMA journal_mode = WAL` and `SQLITE_IOERR_TRUNCATE` failures this finding previously cited **did not reproduce in any run**; treat them as retired. WAL multi-process writing on one host, with an exact counter and no lost updates, is exactly what the store was picked for and it delivers it. What blocks the scale-out is three application-level choices, all of them removable:
  1. `acquireWriterLock` takes `BEGIN EXCLUSIVE` on `.writer-lock.db` in the shared `SQLITE_DIR` before the server listens, so **process two exits at startup by design** — asserted by `tests/process/sqlite-writer-lock.test.ts`. Its stated justification is that a second instance “stalls every fail-closed limiter into a 503 rather than degrading”; the measurement above does not support that — eight concurrent writers produced zero 503-shaped failures.
  2. `serve.reusePort: false` stops two processes sharing the port. Bun documents `SO_REUSEPORT` load balancing as **Linux-only**, so on the ubuntu-24.x target flipping this is the supported path; on Windows it is not (unmeasured here — no Linux host available).
  3. `lib/schedule.ts` registers both cron jobs in **every** process, so N workers run N copies of the SQLite sweep and N copies of the nightly retention sweep.
- **Impact:** Only (3) is a correctness defect — duplicated retention sweeps racing each other on the same rows. (1) is the hard blocker: it turns the intended “scale up the box, add Bun processes” into a startup failure. The measured cost of the model that replaces it is throughput, not correctness: aggregate write rate does **not** improve with processes — one process reached 4,879 writes/s, eight reached 3,302 writes/s aggregate, because SQLite serialises writers. That is ample for a limiter writing one small row per request, but it means SQLite buys cross-process **correctness** here, not write scalability, and the second-order risk is latency coupling: `bun:sqlite` is synchronous, so a worker waiting out `BUSY_TIMEOUT_MS` (2,000 ms) blocks its entire event loop, not just one request.
- **Remediation:** Remove the writer lock, or narrow it from “one process per directory” to what it actually needs to protect; the measurement above is the evidence that a shared directory is safe for N processes. Give the two scheduled jobs a single owner — an advisory lock in the SQLite file itself, or an elected worker — so N processes do not run N sweeps. Then set `reusePort: true` on Linux and keep the current fail-loud second-bind behaviour elsewhere. **Do not reach for `node:cluster` as the Windows answer:** measured on this host, three `cluster.fork()` workers each calling `Bun.serve` on one port served 30 concurrent fresh TCP connections (`Connection: close`) entirely from one PID — `{"distinct":1}` every run, with an empty `bindErrs` and `cluster.schedulingPolicy === SCHED_RR`; a `node:http` control behaved identically, and Bun's docs confirm “Linux only — Windows and macOS ignore the `reusePort` option” (https://bun.com/guides/http/cluster). Outside cluster the second bind does fail loudly on Windows with `EADDRINUSE`, which is what `app.ts:125` relies on; inside cluster it succeeds silently, so a scale-out developed and smoke-tested on Windows would look correct while running single-worker. If cluster is ever adopted, assert distribution rather than a successful `listen`. Add a process-tier test that starts N workers against one `SQLITE_DIR` and asserts the limiter counter is exact and each scheduled job ran once.

### Low — An exported SVG validator is both incorrect and dead outside its expected-failure test

- **Location:** `utils/images/svg-optimizer.ts:326-336` (`validateSvgFile`) and `tests/unit/upload-validation.test.ts:569-619`
- **Evidence:** The helper decides from `file.type`, the filename suffix, and size without reading any content, so PNG bytes named `payload.svg` with `image/svg+xml` return `null` (valid). The repository records that behavior with `test.failing`. A reference sweep finds no application caller: the only import and calls are in that unit-test block. The real upload route instead runs `validateMagicBytes` and then `sanitizeSvgServer`, which rejects the same payload, so this is not a current endpoint bypass.
- **Impact:** The exported name promises validation while its implementation only checks metadata, leaving a trap for the next caller and an intentionally failing test in the default suite for code production never uses. Keeping this parallel, weaker boundary also obscures which upload validator is authoritative.
- **Remediation:** Remove `validateSvgFile` and its expected-failure-only tests, keeping the server upload pipeline as the single validation boundary. If a client-side precheck is still desired later, name it as a metadata precheck and do not present it as a security/content validator.

### Medium — OTP block responses reveal whether an account exists on two anonymous verification paths

- **Location:** `app/api/auth/forgot-password/reset/handler.ts:163-181` (recovery error collapse), `lib/auth/passwordless.ts:262-267` and `lib/auth/api-error.ts:23-30` (passwordless error translation), and `utils/otp.ts:988-1152` (`processOtpVerify` block transition)
- **Evidence:** `processOtpVerify` changes the fifth wrong code for an existing proof from a generic 400 into a 429 carrying the block message and `Retry-After`. The ordinary contact-verification handler explicitly collapses this account-dependent 429 at `app/api/auth/otp/verify/handler.ts:132-139`, but recovery preserves every 429 and passwordless preserves it through `toAuthApiError`. An isolated integration probe using `app.handle`, real PostgreSQL transactions and limiter state, and the test CAPTCHA/mail seams produced the following decisive sequence on both endpoints: four `400` responses for a real account, then `429` with `Retry-After: 21600` and the block message; an unknown account returned the generic `400` with no header. Every response still paid the 1.5-second timing floor. The temporary probe and database clone were removed. Existing enumeration tests compare only the first wrong code with an unknown address, not threshold parity.
- **Impact:** An anonymous caller who can solve the public CAPTCHA can request a code for an address and distinguish an active account in five guesses by status, header, and body. The same requests also put a real proof into a six-hour blocked state (a resend can clear it), while an unknown address has no proof row to block.
- **Remediation:** Give proof-state throttles a distinct internal error kind and collapse that kind to the same generic 400 at every anonymous verification boundary, while preserving 429 from the pre-lookup IP/destination limiters. Add real-versus-unknown parity tests through and beyond the proof-attempt threshold for contact verification, recovery, and passwordless.

### Low — Password proof is recorded as a successful login even when no session is issued

- **Location:** `lib/auth/login-guard.ts:54-59` and `lib/auth/login-guard.ts:279-296` (`verifyLoginAttempt` audit event), `lib/auth.ts:92-150` / `lib/auth.ts:271-325` (sign-in ordering), and the reauthentication calls in `app/api/dash/users/me/change-password/handler.ts:72-78`, `change-email/handler.ts:85-90`, and `change-phone/handler.ts:83-88`
- **Evidence:** Every successful password comparison with `auditMeta` writes `newData.loginSuccess: true`. During sign-in this happens in Better Auth's `before` hook, before the session-creation hook can reject an inactive role, a missing required role, or an unverified contact. The same helper and event are used to prove the current password for three already-authenticated mutation routes. For example, change-email logs `loginSuccess` and can then reject the request because the submitted address is unchanged. Existing self-service audit assertions inspect mutation rows but never assert the extra `users` event, and no sign-in test checks that a rejected post-password gate leaves no success event.
- **Impact:** Forensic queries and alerts cannot treat `loginSuccess` as evidence that a session was issued: routine reauthentication and fully rejected requests produce the same marker. An investigation can therefore overcount successful logins or infer account access that never occurred.
- **Remediation:** Record the event as a purpose-labelled password proof (for example `passwordVerified: true`, `purpose: 'reauth_change_email'`) and emit `loginSuccess` only after session issuance succeeds. Add audit assertions for rejected role/contact gates and for successful and rejected self-service reauthentication.

### Low — Removing an OTP HMAC key while its codes are live creates an anonymous 500 oracle

- **Location:** `lib/auth/otp-hash.ts:85` (`verifyOtpCode`), `lib/auth/keyring.ts:242-248` (`byId`), and `utils/otp.ts:1056` (`processOtpVerify`)
- **Evidence:** OTP envelopes retain their key ID, but `verifyOtpCode` deliberately lets `getOtpKey` throw when that ID is absent. `processOtpVerify` does not classify or normalize the error, so the transaction rolls back and the anonymous HTTP boundaries turn it into a 500. An unknown identifier takes the normal generic 400 path. The focused pinned-runtime check `bun test tests/unit/otp-hash.test.ts` passed all 18 tests, including `a code whose key was REMOVED throws rather than reporting a wrong code`; it does not exercise response parity.
- **Impact:** If an operator removes the previous key during the ten-minute live-code window, every legitimate code issued under it fails and callers can distinguish a real live proof from an unknown account by 500 versus 400. This is bounded to a mis-timed rotation and the remaining lifetime of affected codes.
- **Remediation:** Retain retired OTP keys for longer than the maximum code lifetime and make that grace period an enforceable rotation procedure. At the shared anonymous verification boundary, log a missing generation without identifiers or secrets and return the same invalid/expired response as an unevaluable or absent proof. Add HTTP parity tests covering a removed key on contact verification, recovery, and passwordless verification.

### Low — A timed-out background drain closes stores underneath the still-running work

- **Location:** `lib/schedule.ts:124-150` (`stopAndDrain`), `lib/http/after-response.ts:100-127` (`drainAfterResponse`), `server.ts:304-334` (`shutdown` / `closeStores`), `scripts/smoke.ts:215-230`, and `tests/process/shutdown-lifecycle.test.ts:17-65`
- **Evidence:** Both drains are advisory: neither cancels the work it waits for, and both report a timeout by returning `false`. On the schedule path `shutdown` then returns from inside its `try`, but JavaScript still executes the `finally` and closes PostgreSQL, both SQLite stores, and the writer lock while that callback remains in flight; the forced-exit timer is left to terminate the process later. The database-retention job can await R2 and then resume with PostgreSQL work, so this ordering can use a closed store. The after-response path reaches the same `finally` by falling through: a timed-out `drainAfterResponse` only logs `after-response drain timed out` and continues to `closeStores()`. That queue carries the deferred OTP provider call every anonymous send enqueues (`app/api/auth/otp/send/handler.ts:156`, `app/api/auth/forgot-password/send/handler.ts:105`, `app/api/auth/passwordless/send/handler.ts:225`), and its own failure handler calls `refundFailedDelivery` -> `withTransaction` on the pool `closeStores` has just closed. The 10 s `AFTER_RESPONSE_DRAIN_MS` is smaller than the worst case it waits on: `sendOtpEmail` uses Nodemailer with four independent 5 s timeouts (`utils/otp.ts:27,40-44`). Coverage misses the coordinator: the schedule-timeout fixture exits immediately after its synthetic “stores closed” line, while the lifecycle fixture reimplements `app.stop` and store closure instead of spawning `server.ts`; the smoke script awaits but discards the real server's exit result. No test drives a timed-out after-response drain at all.
- **Impact:** A shutdown that overlaps a slow retention sweep can produce a closed-store failure and leave that retention pass incomplete during the final roughly 15-20 seconds before forced exit. On the after-response path, a slow OTP delivery that fails after the 10 s drain expires cannot be refunded: the stored code and the consumed send attempt survive, so a user whose message was never delivered loses one of `OTP_MAX_ATTEMPTS` and must wait out the backoff ladder. Both are shutdown-only availability/correctness defects rather than data loss.
- **Remediation:** Treat “drain timed out” as a reason to keep the stores open until forced exit, in one place covering both queues — or add cancellation and await confirmed termination before `closeStores()` runs. Test the real `server.ts` coordinator for clean, half-sent-request, active-sweep-timeout, and pending-after-response-task shutdowns; assert store/job ordering, the structured stop event, and the spawned process exit code in both lifecycle tests and smoke.

### Low — Configuration comments retain change history and tool archaeology beyond the current rationale

- **Location:** representative blocks at `server.ts:20-48`, `scripts/require-bun.mjs:4-66`, `bunfig.toml:1-51`, `eslint.config.mjs:15-45`, `knip.jsonc:4-58`, and `tests/helpers/preload-base.ts:64-80`
- **Evidence:** These comments narrate removed implementations and migrations (“used to,” “previous entry,” old Next behavior, prior probe failures, and exact tool archaeology) over dozens of lines, rather than recording only the current invariant and its irrecoverable reason. That conflicts with AGENTS.md Baseline 4-5 (“comment only where a reader would ask why,” “no change history,” and use the fewest equally informative lines). The maintenance cost is already concrete: this audit found comments that still claimed OTPs used Argon2, delivery failures were not refunded, active OTP purposes were reserved, and provider latency remained on anonymous response paths; those factual conflicts were corrected with permitted comment-only edits.
- **Impact:** Readers must distinguish current contracts from historical narrative, and implementation changes can leave authoritative-looking but false operational/security claims beside otherwise correct code. The comments also duplicate benchmark and test evidence that already has a durable home, increasing the number of places a change must keep synchronized.
- **Remediation:** Condense each remaining block to the current invariant plus the shortest non-obvious reason. Keep reproducible measurements in the referenced benchmark report, behavioral examples in tests, and migration history in version control or a dedicated design document; retain a short pointer where that external evidence is necessary.

### Low — The development-only endpoint stays registered in production, and the routing boundary advertises it

- **Location:** `routes.ts:283-292` (the dev-only block and its `TODO: remove this endpoint in production`), `app/api/dev/sign-up/handler.ts:45-50`, and `lib/http/route-manifest.ts:145-156` (`isUndocumentedPath` / `toPublishedManifest`)
- **Evidence:** The `/api/dev/*` prefix already has a production concept — `isUndocumentedPath` — but it only filters the published OpenAPI document; the route is still added to `ROUTES` unconditionally, so it keeps a real registration, the 405 boundary and the route-aware OPTIONS gate. The environment gate lives inside the handler instead of at that shared boundary. Probed in-process against the real app with `NODE_ENV=production` (`bun -e` driving `app.handle`, R2/origin vars set to throwaway values): `POST /api/dev/sign-up` → `403` with the distinctive body `هذه النقطة متاحة فقط في بيئة التطوير`; `GET /api/dev/sign-up` → `405 Allow: POST, OPTIONS`; `OPTIONS /api/dev/sign-up` → `204`. A genuinely unrouted `/api/dev/does-not-exist` answered `404` for all three methods. The route also carries `preAuth: 'none'`, so the production rejection runs with no admission limit. Tests cover only the document filter (`tests/unit/openapi-contract.test.ts:136-155`); nothing asserts the runtime boundary outside development, and `tests/helpers/run.ts:53` runs the database tiers as `development`, where the endpoint is live.
- **Impact:** A production deployment confirms to any unauthenticated caller that it carries a dev sign-up endpoint, by status code and by `Allow`. That is reconnaissance value, not access — the handler fails closed today, and its guard is a positive comparison against `'development'`. The exposure is structural: the only thing keeping it harmless is one `NODE_ENV` string comparison plus a `TODO` nothing enforces, and on the development branch this endpoint mints a `ROLE_SCOPE.SYSTEM` role with every permission of every page set `true` from an unauthenticated request (`handler.ts:65-113`). A future `/api/dev/*` route that omits or misspells the guard ships live and unauthenticated with nothing failing the build, the boot, or the suite.

The refusal is trivially testable in the unit tier, where `bun test` forces `NODE_ENV=test`. Add a test asserting that a production-mode route table registers no `/api/dev/` path, that the path answers 404 on every method, and that the handler refuses under a non-development `NODE_ENV`.

- **Location:** `lib/http/openapi.ts:252-268` (`ENVELOPE_SCHEMA.meta`), against `utils/api-response.ts:20-25` (`PaginationMeta`) and `lib/http/contract.ts` (`HandlerEnvelope`)

### Low — The retention sweep cannot report a degraded run, so a total R2 outage logs as a completed one

- **Location:** `db/maintenance.ts:102-112` (`DatabaseSweepResult.status: 'ok'`), `db/maintenance.ts:257-323` (`sweepTempFiles`), `db/maintenance.ts:333-355` (`runDatabaseSweep`), against `lib/sqlite/maintenance.ts:173-189` (`MaintenanceSweepResult.status`) and `lib/schedule.ts:33-47` (`logRun`)
- **Evidence:** The two scheduled jobs share one `SweepOutcome` contract (`lib/schedule.ts:8-12`, `status: 'ok' | 'degraded'`) and disagree on how to use it. The SQLite sweep states the rule explicitly — “`degraded` when a store could not be swept. Containment is not the same as success … reporting the run as `ok` afterwards told the scheduler — and any alert built on it — that maintenance had completed” — and `tests/integration/cache-maintenance-failure.test.ts:27-30` asserts it. Its counterpart types `status` as the literal `'ok'`, so `runDatabaseSweep` cannot express the state at all. `sweepTempFiles` has exactly the contained failure the rule was written for: an R2 delete that throws is absorbed by `Promise.allSettled`, counted, logged as `db.sweep.r2DeleteFailed`, and reported only through `hasMore` — which is indistinguishable from an ordinary backlog. `logRun` then writes `scheduled sweep completed` with `status: "ok"` to stdout. `tests/integration/retention-sweep.test.ts:432-434` pins this: under a forced `DeleteObject` failure it asserts `hasMore === true` **and** `status === 'ok'`, and the comment beside it defends only the `hasMore` half. The module's own header calls this the one sweep that IS a correctness boundary — “nothing else in the codebase ever deletes a temporary upload, so if this does not run, R2 objects accumulate and are paid for indefinitely” (`db/maintenance.ts:15-20`).
- **Impact:** During an R2 outage or a credential/permission mistake, the nightly retention pass deletes no objects and removes no `files` rows, yet the scheduler reports it as completed. A monitor built on the degraded signal the sibling job defines — the natural thing to alert on, and the only sweep-level status either job emits — stays silent while temporary uploads accumulate in the bucket and are billed indefinitely. The `db.sweep.r2DeleteFailed` line on stderr is the only thing that fires, so the blind spot is real but not total.
- **Remediation:** Widen `DatabaseSweepResult.status` to `'ok' | 'degraded'` and return `degraded` when any R2 delete in the run failed, matching the rule `lib/sqlite/maintenance.ts` already states; update the retention test to assert `degraded` under a failing object store, keeping the existing `hasMore` assertions.

### Medium — A `<use>` reference chain expands to ~10³⁷ rendered nodes while passing every structural gate
