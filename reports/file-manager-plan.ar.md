# مدير الملفات / مكتبة الوسائط — خطة البنية التحتية والتنفيذ (v3)

**الحالة:** خطة، لا يوجد كود إنتاجي بعد. يُدمج الإصدار v3 إجابات المالك المؤرخة في 2026-09-04 (دعم الملفات العامة والخاصة معاً؛ عمل الواجهة والـ API على نفس النطاق `same-origin`؛ رسائل باللغة العربية؛ دعم المستندات في الإصدار الأول؛ وحرية إجراء تجارب عملية Spike)، بالإضافة إلى معالجة قاعدة ثابتة (Invariant) في المستودع كان الإصدار v2 يخالفها (القسم 6.0). يوثق القسم 12 نتائج مراجعات الكود؛ بينما يوثق القسم 13 نتائج القياس والتجارب العملية (Spike).

**الواجهة الخلفية (Backend):** هذا المستودع (Bun + Elysia، جدول المسارات في `routes.ts`).  
**واجهة المستخدم (UI):** في المستودع المجاور `../soft-house-dash-2` (Next 16 Pages Router، TanStack Query + Table، Radix، dnd-kit، react-dropzone، zustand، sonner)، وتعمل على نفس نطاق الـ API (Same-Origin).

**مقاس عملياً (measured)** = تم التحقق منه على الـ Bucket العام الحقيقي في Cloudflare R2 (بتاريخ 2026-09-03/04، باستخدام مسارات تجريبية مؤقتة تم حذفها لاحقاً)، أو على قاعدة بيانات PostgreSQL التجريبية (بتاريخ 2026-09-04، جداول مؤقتة تم حذفها — انظر القسم 13).  
**غير متحقق منه (unverified)** = ادعاء أو افتراض لم أتمكن من اختباره.

## 1. ملخص القرارات الأساسية

| المسألة / السؤال                           | القرار المعتمد                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| :----------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **المرجع الأساسي لشجرة المجلدات**          | **PostgreSQL** (جدولا `folders` + `files`). يُعد R2 مجرد مخزن للبيانات الخام (Blob store)، ولا يتم الاستعلام منه نهائياً لعرض أي صفحة.                                                                                                                                                                                                                                                                                                           |
| **الـ Buckets**                            | **اثنان Bucket**، واحد لكل مستوى رؤية (عام / خاص)، وكلاهما اختياري عبر `.env` (القسم 2.5). نظراً لأن ربط الدومين الخاص (Custom Domain) ينشر الـ Bucket بالكامل للعامة، فلا يمكن لحاوية واحدة جمع النوعين معاً بأمان.                                                                                                                                                                                                                             |
| **مستوى الرؤية والخصوصية (Visibility)**    | خاصية تنتمي إلى **جذر الشجرة الفرعية للمجلد (Folder Subtree Root)**، وتُورّث وتُفرض عبر مفتاح أجنبي مركب (Composite FK) **(مقاس عملياً)**. ترث الملفات خصوصية المجلد التابعة له. وترفض قاعدة البيانات عمليات النقل بين مجلدات مختلفة الخصوصية. أما عمليات الرفع التابعة للكيانات، فتأخذ خصوصيتها من سياسة سيرفر صارمة لكل مورد، ولا يحددها العميل أبداً لكل ملف على حدة.                                                                         |
| **مفاتيح كائنات R2 (Object Keys)**         | **مبهمة وغير قابلة للتغيير (Opaque and Immutable):** `m/<yyyy>/<mm>/<file id>.<ext>`. عمليات إعادة التسمية أو النقل تعدل في قاعدة البيانات فقط.                                                                                                                                                                                                                                                                                                  |
| **نموذج المجلدات (Folder Model)**          | قائمة تجاور (Adjacency list)، قيد فريد `(parent_id, lower(name))`، عمق الشجرة ≤ 10، وعدد العناصر الفرعية ≤ 500، وتُفرض جميعها بشكل غير قابل للتعارض داخل المعاملة (Transactionally).                                                                                                                                                                                                                                                             |
| **دورة حياة الملف (Lifecycle)**            | نوع مخصص (Enum) لحالة الملف `status`: `pending → active → deleting`. لا يمكن لأي كيان خارجي الإشارة إلا للملفات النشطة `active` فقط، ويُفرض ذلك عبر مفتاح أجنبي مركب `(file_id, file_status) → files(id, status)` **(مقاس عملياً، القسم 6.2)**.                                                                                                                                                                                                  |
| **الشبكة مقابل المعاملات (Network vs Tx)** | **يُمنع منعاً باتاً فتح معاملة (Transaction) في قاعدة البيانات أثناء انتظار اتصال شبكي بـ R2** (قاعدة ثابتة في `db/limits.ts`). عمليات الرفع والحذف تتم على مرحلتين، ويعمل عمود الحالة `status` كعلامة خطوة ثابتة ودائمة.                                                                                                                                                                                                                        |
| **مسار الرفع (Upload Path)**               | **يمر عبر السيرفر (Server-proxied)**، ملف واحد لكل طلب. مسار جديد `POST /api/dash/media/files` للمكتبة؛ ومسار `/api/upload/file` (أعيدت تسميته من `/api/upload/image`) لرفع ملفات نماذج الكيانات. كلاهما يعتمد على نفس وحدة المعالجة المشتركة.                                                                                                                                                                                                   |
| **أنواع الملفات (File Types)**             | **قائمة سماح حسب النوع (Allowlist by kind):** الصور: PNG, WebP, SVG (عبر المسار القائم). المستندات: دعم الـ PDF في الإصدار الأول؛ الجدول قابل للتوسيع لكل مشروع، ويجب أن يتضمن كل إدخال فحصاً للتوقيع الرقمي للبيانات (Magic bytes). ويتم رفض أي شيء آخر.                                                                                                                                                                                        |
| **روابط التوزيع (Delivery URL)**           | للـ Bucket العام: رابط الدومين الخاص. للـ Bucket الخاص: رابط موقع مسبقاً (Presigned GET) عبر نقطة نهاية S3 (يعمل كـ Bearer token، صلاحية ≤ ساعة واحدة). التنزيلات تستخدم دائماً روابط موقعة مع خاصية `attachment`.                                                                                                                                                                                                                               |
| **الربط مع الكيانات (Entity Association)** | مفاتيح أجنبية صارمة (Strict FKs) من جداول الكيانات المالكة (عمود مباشر أو جدول وسيط)، مع خيار `on delete no action`. يوجد سجل كودي لمصادر الاستخدام للإجابة على سؤال "أين يُستخدم؟". تم إلغاء عمودي `files.contextTable/contextId`.                                                                                                                                                                                                              |
| **آلية الحذف (Deletion)**                  | **المرحلة A (معاملة):** قفل، وتحويل الحالة إلى `status='deleting'` — يرفض المفتاح الأجنبي المركب العملية فوراً إذا كان الملف مستخدماً، وقبل فقدان أي بايت. **المرحلة B (بدون معاملة):** حذف الكائنات من R2 عبر `DeleteObjects`. **المرحلة C (معاملة):** حذف صفوف الملفات من الداتابيز. يُعاد محاولة حذف الصفوف المعلقة في حالة `deleting` عبر فحص التنظيف الدوري. حد الدفعة ≤ 50. حذف المجلدات الفارغة فقط. لا توجد سلة مهملات في الإصدار الأول. |
| **الصلاحيات (Permissions)**                | صفحة جديدة `media`: `view`, `create`, `edit`, `editOwn`, `delete`, `deleteOwn`. يمنحها ملف الترحيل للأدوار ذات النطاق النظامي (System-scope).                                                                                                                                                                                                                                                                                                    |
| **الرسائل (Messages)**                     | باللغة العربية، داخل ملف `messages.ts` بجانب المعالجات (Handlers)، مثل باقي مسارات النظام.                                                                                                                                                                                                                                                                                                                                                       |

### لماذا المفاتيح المبهمة وغير القابلة للتغيير؟

تغيير المفاتيح في R2 عند إعادة التسمية أو النقل يعني تنفيذ `CopyObject` ثم `DeleteObject` لكل كائن، و**سيؤدي ذلك إلى كسر جميع الروابط العامة المضمنة مسبقاً في المحتوى (المقالات، الصفحات، الإيميلات)**. بوجود المسار داخل قاعدة البيانات، تصبح إعادة تسمية مجلد مجرد استعلام `UPDATE` واحد، ذري وفوري وبدون كسر أي رابط.

المفاتيح لا تحتوي على اسم الملف الأصلي (لأنه يصبح قديماً بعد أول إعادة تسمية، ويسرّب اسم الملف الأصلي في الروابط العامة)؛ ولا تحتوي على بادئة اسم الكيان (لأن نموذج الإنشاء لا يملك معرف مالك بعد). معرّف الملف (UUID) هو الاسم الأساسي للمفتاح، لذا فإن حدوث تعارض مستحيل إلا في حال وجود خطأ برمجي؛ ومع ذلك يتم إرسال رأس الحماية `If-None-Match: *` كإجراء وقائي **(تم قياسه: يُرجع 412 إذا وُجد المفتاح مسبقاً)**، ويُعامل الخطأ 412 كفشل في القواعد الثابتة — يتم تسجيله ويفشل الطلب ولا يتم حذف أي شيء.

## 2. التوافق مع واجهة Cloudflare R2 S3 API

المصادر: وثائق Cloudflare الرسمية لـ S3 API، الحاويات العامة، الروابط الموقعة، والتناسق (Consistency) (تم جلبها في 2026-09-03/04)، بالإضافة إلى الاختبارات الحية.

### 2.3 العمليات المركبة (في حال اضطررنا لتغيير المفتاح)

تستخدم فقط لعمليات الترحيل اليدوية المخططة (مثل نقل كائن من حاوية عامة إلى خاصة)، وليس لنقل/تسمية الملفات في الواجهة:

1. `CopyObject` مع ترميز `CopySource`، وتعيين `MetadataDirective: REPLACE`، وإعادة إرسال الرؤوس.
2. `HeadObject` على الهدف؛ ومقارنة `ContentLength` وحساب SHA-256 مخزن مسبقاً (**وليس** مقارنة ETag؛ لأن ETag للملفات المجزأة لا يمثل تجزئة للمحتوى).
3. تحديث صف الملف في المعاملة.
4. `DeleteObject` للمصدر (الفشل هنا يترك كائناً يتيماً تكتشفه وظيفة المطابقة لاحقاً).
5. أي فشل قبل تحديث الداتابيز: حذف الهدف، وترك الصف كما هو.

**نطاق المنطقة الجغرافية (Region Scope):** الكود في `lib/r2/client.ts` يثبت `region: 'weur'`. الوثائق توصي بـ `auto`. **تم قياسه:** كلاهما مقبول؛ سيتم التحويل إلى `auto` في المرحلة 0.

**الروابط الموقعة للرفع (Presigned PUT):** افتراضياً توقّع مكتبة SDK رأس `host` فقط، لذا يُقبل الملف حتى لو تغير `Content-Type`. عند إضافة `signableHeaders: new Set(['content-type'])`، يتم التحقق ويرفض R2 الطلب بكود 403 عند عدم التطابق. يتم التحقق من الحجم في الحالتين. ولكن الروابط الموقعة لا يمكنها التحقق من محتوى البايتات الحقيقي (Magic bytes، تنظيف SVG، ضغط WebP، توقيع الـ PDF). لذلك يظل الرفع عبر خادم التطبيق (Server-proxied) هو الخيار المعتمد.

### 2.4 التوزيع، التخزين المؤقت (Cache) والـ CORS

- **رابط الـ Bucket العام = دومين مخصص (Custom Domain)، وليس `r2.dev`** (حيث تنص وثائق كلاود فلير على أنه مخصص للتطوير ومحدود بالمعدل). يجب ألا يشارك الدومين المخصص نطاق الكوكيز (Cookie scope) مع لوحة التحكم: لأن الحاوية العامة تخدم ملفات SVG و PDF، وأي ثغرة فيها ستعمل على نطاق كوكيز لوحة التحكم إن لم تكن معزولة.
- **الكاش مقابل الحذف:** تُكتب الكائنات غير القابلة للتغيير مع ترويسة `public, max-age=31536000, immutable`. يقوم الدومين المخصص بالتخزين على حافة الشبكة (Edge Cache)، لذلك قد يستمر تقديم الملف المحذوف حتى تنتهي صلاحية نسخته المخزنة مؤقتاً أو يتم تفريغها (Purge). هذا مقبول في الإصدار الأول MVP؛ وإضافة توكن تفريغ الكاش ستكون في المرحلة 3.
- **CORS:** عناصر `<img>` والروابط لا تحتاج إلى CORS. تحتاجه فقط طلبات `fetch()` المباشرة أو الرفع المباشر. في الإصدار الأول: المعاينة تتم عبر `<img>`؛ ومعاينة المستندات تتم عبر فتح الرابط الموقع في **تبويب جديد** (نطاق معزول)؛ والتنزيلات عبر رابط موقع بـ `attachment`. لذا **لا حاجة لقواعد CORS على الحاوية في MVP**. تُضاف فقط مسارات النطاقات إلى سياسة أمان المحتوى (CSP `img-src`) في الفرونت إند.

### 2.5 حسم مسألة الدومين المخصص والحاويات

ربط دومين مخصص ينشر **الـ Bucket بالكامل للعامة**: لا توفر Cloudflare أي حظر للمسارات داخل الحاوية إلا باستخدام منتجات أمنية خارجية (WAF / Access Rules)، وهذا ينقل الأمان لخارج المستودع وغير قابل للاختبار البرمجي وغلطة واحدة قد تسرب كل الملفات الخاصة. لذلك، الاعتماد على **حاويتين (Two Buckets)** هو الحل الصحيح والمعتمد برمجياً في الـ Schema (`bucket_type`).

إعدادات البيئة بالكامل عبر ملف `.env`:

| المتغير             | المعنى                                                                       | القاعدة                                                                                                                                                                    |
| :------------------ | :--------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `R2_PUBLIC_BUCKET`  | اسم الحاوية العامة                                                           | اختياري. يُفعّل مستوى الرؤية `public`.                                                                                                                                     |
| `R2_PUBLIC_URL`     | الدومين المخصص للحاوية العامة، يبدأ بـ `https://` بدون شرطة مائلة في النهاية | **إلزامي كلما تم ضبط `R2_PUBLIC_BUCKET`** (لأن وجود حاوية عامة بروابط لا يمكن الوصول إليها يُعد خطأ في الإعداد). يسبب خطأ إيقاف تشغيل (Boot error) في جميع البيئات إن غاب. |
| `R2_PRIVATE_BUCKET` | اسم الحاوية الخاصة                                                           | اختياري. يُفعّل مستوى الرؤية `private`.                                                                                                                                    |
| بيانات الاعتماد     | `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`                  | إلزامية في الإنتاج عند ضبط أي حاوية.                                                                                                                                       |

يجب تفعيل حاوية واحدة على الأقل في الإنتاج. يستنتج الملف `lib/r2/client.ts` الحاويات المفعلة `ENABLED_VISIBILITIES`؛ ومحاولة إنشاء مجلد أو رفع ملف لحاوية معطلة يُرجع خطأ 422؛ وترسل الـ API الحاويات المفعلة للواجهة لتخفي الخيارات غير المتاحة تلقائياً.

## 3. بنية المجلدات (Folder Architecture)

### 3.1 مقارنة الخيارات المدروسة

| وجه المقارنة                       | أ. الاعتماد على بادئات R2 الافتراضية (`ListObjectsV2` + `Delimiter`)                                              | ب. فهرس كامل في قاعدة البيانات (الخيار المعتمد)                   |
| :--------------------------------- | :---------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------- |
| **عرض المجلد**                     | استدعاء أو أكثر لكل صفحة، ~250–600 مللي ثانية لكل استدعاء **(مقاس عملياً)**، ترتيب أبجدي فقط، صفحات من 1000 مفتاح | استعلام مفهرس واحد وسريع، بأي ترتيب مطلوب                         |
| **الترتيب / الفلترة / البحث**      | مستحيلة من طرف السيرفر                                                                                            | مدعومة أصلياً عبر محلل الجداول القائم `lib/data-table/parsers.ts` |
| **المجلدات الفارغة**               | تحتاج إنشاء كائنات وهمية فارغة `prefix/` (وتظهر كعنصر داخل نفسه ويجب فلترتها)                                     | صف عادي وبسيط في جدول المجلدات                                    |
| **إعادة تسمية/نقل مجلد**           | نسخ ثم حذف كل كائن بداخله؛ وتتغير الروابط                                                                         | استعلام `UPDATE` واحد، وفوري                                      |
| **البيانات الوصفية ومستوى الرؤية** | عبر `x-amz-meta-*` فقط، غير قابلة للبحث، وتحتاج استدعاء `HeadObject` لكل ملف؛ لا تدعم نموذج الخصوصية              | أعمدة وعلاقات مفاتيح أجنبية متكاملة                               |
| **انحراف البيانات (Drift)**        | منعدم (المخزن هو الحقيقة)                                                                                         | وظيفة مطابقة ومزامنة تقرأ الفروقات، للقراءة فقط في المرحلة 1      |

### 3.2 تعديلات قاعدة البيانات (`db/schema.ts`، ترحيل واحد؛ الترتيب في القسم 10)

```sql
file_status  enum ('pending','active','deleting')          -- جديد
bucket_type  enum ('public','private')                     -- موجود مسبقاً، يُعاد استخدامه لمستوى رؤية المجلدات

folders
  id           uuid pk (uuidv7)
  parent_id    uuid null → folders.id                                     (null = جذر الشجرة)
  visibility   bucket_type not null
  name         varchar(100) not null      -- نصوص موحدة الترميز NFC، مقلمة، بدون '/'، وبدون حروف تحكم
  created_by   uuid null → users.id on delete set null
  timestamps
  unique (id, visibility)                                                 -- هدف المفتاح الأجنبي
  foreign key (parent_id, visibility) references folders (id, visibility) -- يرث الابن خصوصية الأب إجبارياً، وتمنع النقل بين خصوصيات مختلفة (مقاس عملياً)
  unique index ux_folders_parent_name on (parent_id, lower(name)) where parent_id is not null
  unique index ux_folders_root_name   on (lower(name))           where parent_id is null
  فهرس trigram على name

files (تعديلات)
  + status        file_status not null default 'pending'              -- يستبدل is_temporary
  - is_temporary                                                       -- يُحذف بعد ترحيل البيانات القديمة
  + folder_id     uuid null
  + display_name  varchar(150) not null                               -- يضاف قابلاً للقيمة الفارغة ثم يملأ من اسم المفتاح ثم NOT NULL
  + kind          file_kind enum ('image','document') not null
  ~ size_bytes    bigint
  - context_table, context_id, enum file_context_table                 -- تحذف بالكامل (القسم 5.2)
  unique (id, status)                                                  -- هدف للمفاتيح الأجنبية للكيانات المرتبطة
  foreign key (folder_id, bucket_type) references folders (id, visibility)   -- يطابق الـ bucket الخاص بالملف خصوصية مجلده إجبارياً (مقاس عملياً)
  فهارس: (folder_id, created_at, id), (folder_id, lower(display_name), id), (status, created_at) where status <> 'active'
  فهرس trigram على display_name

referrers (في كل مشروع؛ القاعدة الصارمة التي يجب على كل جدول مرتبط اتباعها)
  file_id      uuid not null
  file_status  file_status not null default 'active' check (file_status = 'active')
  foreign key (file_id, file_status) references files (id, status) on update no action on delete no action
```

- المفتاح الأجنبي المركب هو الذي يجعل الحذف آمناً تماماً من تعارضات التوقيت (TOCTOU) دون الحاجة لفتح معاملات عبر الشبكة (القسم 6.2). **تم قياسه واختباره:** لا يمكن وضع علامة `deleting` أو حذف ملف نشط مرتبط بكيان؛ ولا يمكن ربط أي كيان بملف حالته `pending` أو `deleting`؛ وفي حالات التزامن يتم حظر العملية الثانية ثم رفضها.
- استخدام `NO ACTION` وليس `RESTRICT`: لأن `RESTRICT` في PostgreSQL ترفع رمز الخطأ `SQLSTATE 23001 restrict_violation`، وهو ما لا تتعرف عليه دالة فحص أخطاء المفاتيح الأجنبية القائمة في المشروع `isForeignKeyViolation` (التي تفحص `23503` فقط). ستوسع المرحلة 0 الدالة لتدعم كلا الرمزين.
- إضافة `media` لصفحات الداشبورد `DASHBOARD_PAGES` وضبط صلاحياتها التلقائية في `DEFAULT_PAGE_PERMISSIONS`: تشمل `view`, `create`, `edit`, `editOwn`, `delete`, `deleteOwn`. ولا وجود لـ `viewOwn` (لأن مكتبة لا يرى المستخدم فيها سوى ملفاته ليست مكتبة وسائط مشتركة).
- يمنح ملف الترحيل صلاحيات صفحة `media` تلقائياً للأدوار ذات النطاق النظامي `scope = 'system'` لضمان عدم حظر مدراء النظام (Super-admin) من الصفحة الجديدة.
- أقصى عمق للمجلدات 10، والحد الأقصى للعناصر الفرعية 500 تُفرض بالمعاملات. الترتيب الثانوي دائماً على `id` لمنع التخبط. أسماء الملفات يمكن أن تتكرر، بينما أسماء المجلدات داخل نفس المستوى فريدة (دون تحسس لحالة الأحرف).

### 3.3 دقة واستخراج المسارات (Path Resolution)

تتعامل واجهة المستخدم مع المجلدات عبر المعرّف (`?folder=<uuid>`)؛ ويتم استخراج مسار التنقل (Breadcrumbs) عبر استعلام تكراري واحد (Recursive CTE) مقيد بأقصى عمق (10 مستويات). تعرض الصفحة الرئيسية المجلدات الجذرية فقط مع شارة الخصوصية الخاصة بها. لا تمر أي مسارات نصية خام عبر الـ API.

جميع المسارات تخضع للقواعد الموحدة: `preAuth: 'ip-limit'`, `auth: 'permission'`, `response: 'envelope'`, `handlerRateLimit: true`، وتسجيل سطر تدقيق الأمان (Audit) داخل نفس معاملة قاعدة البيانات.

- القراءة: 120 طلب/دقيقة.
- التعديل: 30 طلب/دقيقة بنظام `failClosed`.
- الرفع: للصور تتبع ميزانية الميجابكسل المعتمدة (`UPLOAD_MEGAPIXEL_BUDGET`)؛ وللمستندات تستهلك `max(2, ceil(MiB))` من ميزانية 60 طلب/دقيقة. ميزانيتان في نفس المسار حسب نوع الملف.
- رفع الملفات المتعددة يُدار عبر **طابور في العميل (Client Queue):** إرسال ملف واحد في كل طلب، بمعدل توازي 2 (Concurrency 2)، مع تتبع حالة كل ملف، والتعامل الذكي مع الخطأ 429 عبر رأس `Retry-After`. وسقف السيرفر هو 20 صورة/دقيقة للمستخدم.

## 5. المفاتيح ودورة الحياة والربط مع الكيانات

### 5.1 هيكلية المفاتيح

المسار ثابت لجميع الملفات: `m/<yyyy>/<mm>/<file id>.<ext>`، داخل الحاوية المناسبة لخصوصية الملف. الامتداد يُشتق دائماً من فحص المحتوى الحقيقي (MIME) وليس من الاسم المرسل من العميل.

### 5.2 الربط الصارم ومنع الحذف العشوائي

ترتبط الجداول المالكة بالملفات بإحدى طريقتين، وكلاهما يحمل عمود الحالة المرافق `file_status`:

1. **عمود مباشر:** مثل `projects.cover_image_id` ومعه عمود `cover_image_status`. لصورة واحدة يعاد استخدامها.
2. **جدول وسيط (Junction table):** مثل `project_images(project_id, file_id, file_status, sort_order)`. لعدة ملفات مرتبة.

يمكن للملف الواحد أن يكون داخل مجلد في المكتبة ومستخدماً لدى عدة مشاريع في نفس الوقت. وقاعدة البيانات ترفض حذف أي ملف مستخدم (409). الكيانات العامة ترتبط بملفات عامة والخاصة بخاصة، ويضمن ذلك سجل السياسات واختبارات الوحدة.

### 5.3 سجل الاستخدامات (Usage Registry)

يحتوي `USAGE_SOURCES` على: `{ table, column, resource: DashboardPage, label }` لكل جهة ارتباط. ويغذي قائمة "أين يُستخدم؟" (مع فلترة النتائج بحسب ما يحق للمستخدم رؤيته)، وتحديد نصوص رسائل المنع 409، واختبار تكاملي يفشل تلقائياً إذا أضيف حقل مفتاح أجنبي يشير لجدول الملفات دون تسجيله هنا.

### 5.4 المطالبة بالملفات المؤقتة (Claiming)

دالة `claimFiles(tx, { ids, actorId })`: تنفذ تحديثاً شرطياً `UPDATE files SET status='active' WHERE id = ANY($ids) AND status='pending' AND uploaded_by=$actorId RETURNING id`. إذا كان عدد الصفوف المحدثة لا يطابق عدد المدخلات، تفشل المعاملة فوراً (422)؛ مما يمنع نهائياً ربط ملف حُذف أو استخدمه شخص آخر. **(مقاس عملياً):** من يصل أولاً (المطالبة أو التنظيف) يفوز وتقفل الصفوف دون تعارض.

### 5.5 القواعد الثابتة

- لا يُبنى المفتاح من مدخلات المستخدم؛ ولا يُكشف المفتاح الداخلي `r2Key` للواجهة أبداً.
- الخصوصية تؤخذ من المجلد أو من سياسة السيرفر، ولا يحددها العميل من الطلب.
- حذف الكيان المالك يحذف علاقات الربط فقط في معاملته، بينما تبقى الملفات في المكتبة لاستخدامها مجدداً، إلا إذا طُلب حذفها صراحة عبر دالة الحذف المخصصة.

## 6. تفاصيل السلوك البرمجي (Behaviour Details)

### 6.0 القاعدة الحاكمة لهذا القسم

قاعدة صارمة في المستودع (`db/limits.ts`): **"يُمنع منعاً باتاً إبقاء معاملة قاعدة بيانات مفتوحة أثناء انتظار اتصال شبكي بجهة خارجية"** — حجم مجمع الاتصالات (Pool) هو 10 اتصالات فقط، وعشرة طلبات تنتظر R2 داخل معاملات ستعلق كل العمليات في السيرفر. لذلك لا تفتح أي معاملة أثناء الاتصال بـ R2، ويعمل عمود `status` كمسجل للخطوات.

### 6.1 آلية الرفع (Upload Pipeline)

1. التحقق من الصلاحيات والمعدل وقراءة الملف.
2. التحقق من نوع وتوقيع الملف (MIME + Magic bytes)؛ ورفض ما عداه. الصور: عبر معالج الصور القائم. المستندات: عبر فحص توقيع `%PDF-` وألا يتجاوز الحجم 10 ميجابايت. تم رفع حد جسم الطلب إلى 12 ميجابايت.
3. **المعاملة A:** إدخال الصف في الداتابيز بحالة `status='pending'` مع كامل بياناته، ثم إنهاء المعاملة وحفظ التغيير (Commit).
4. رفع الكائن لـ R2 عبر `PutObject` مع رأس الحماية `IfNoneMatch: '*'`، وتعيين ترويسة التخزين المؤقت، وترويسة التوزيع (`inline` للصور، و **`attachment` للمستندات في الحاوية العامة** لضمان عدم تشغيل الـ PDF تلقائياً على النطاق العام، وتوفر الواجهة رابط معاينة موقعاً مسبقاً).
5. **المعاملة B:** في مسار المكتبة: تحويل الحالة إلى `status='active'`؛ وفي مسار الكيانات: تركه معلقاً `pending` بانتظار عملية المطالبة `claimFiles`. وتدوين سطر التدقيق.
6. في حالات الفشل: فشل رفع R2 ← حذف الصف المعلق فوراً (ويغطيه الفحص الدوري إن تعذر الحذف). فشل المعاملة B بعد نجاح الرفع ← يبقى الملف `pending` وينظفه الفحص الدوري مع كائنه بعد انتهاء المدة المحددة TTL. حدوث الخطأ 412 ← تسجيل خطأ جسيم، وحذف الصف المعلق، و**عدم المساس بالكائن الموجود في R2**.

### 6.2 آلية الحذف ثلاثية المراحل (Three-Phase Deletion)

مسار واحد موحد للطلبات والفحص الدوري والتطهير:

```
المرحلة A (معاملة):   قفل الصفوف عبر SELECT … FOR UPDATE؛
                      تحويل الحالة: UPDATE files SET status='deleting' WHERE id = ANY($ids) AND status IN ('active','pending')
                      ← المفتاح الأجنبي المركب يرفض فوراً لو وجد أي ارتباط خارجي (مقاس عملياً) ← 409 دون تغيير أي شيء
                      كتابة أسطر التدقيق؛ ثم تأكيد المعاملة (COMMIT)
المرحلة B (بدون معاملة): حذف الكائنات من R2 عبر DeleteObjects (بدون فتح أي معاملة داتابيز)
المرحلة C (معاملة):   حذف صفوف الملفات نهائياً: DELETE FROM files WHERE id = ANY($ids) AND status='deleting'
```

- إذا حاول مستخدم ربط الملف أثناء المرحلة A، فسيتم تعليق طلبه حتى انتهاء المعاملة ثم يرفض فوراً لعدم وجود ملف نشط. لا توجد أي نافذة زمنية تسمح بربط ملف على وشك الحذف.
- في حال فشل اتصال R2 في المرحلة B: تظل الصفوف بحالة `deleting`؛ ويقوم الفحص الدوري الليلي بإعادة المحاولة تلقائياً للمرحلتين B و C (عملية الحذف في R2 آمنة وتكرارية). هذا التصميم يصلح نفسه ذاتياً ولا يترك بيانات معلقة في الواجهة.
- يتم تحويل فحص الملفات المؤقتة القديمة في `db/maintenance.ts` ليعتمد على هذا المسار الآمن.
- الحذف مقيد بـ 50 ملفاً لكل طلب من الواجهة. ولا يتم الحذف المتفائل (Optimistic UI) في الواجهة بل تنتظر اكتمال الرد.

### 6.3 استخراج الروابط (URLs)

- `fileUrl`: للحاوية العامة ← رابط الدومين المخصص المباشر؛ للحاوية الخاصة ← رابط موقع مسبقاً صالح لساعة واحدة.
- `downloadUrl`: دائماً رابط موقع مع ترويسة تنزيل `attachment` واسم الملف الحقيقي.
- `previewUrl` للمستندات: رابط موقع بـ `inline` يُفتح في تبويب معزول وجديد. الروابط الموقعة لا تخزن في الداتابيز ولا تسجل في السجلات وتولد عند الطلب فقط.

### 6.4 سجلات التدقيق (Audit)

توثيق عمليات الإدخال والتعديل والحذف على جدولي `files` و `folders`، مع تفاصيل الاسم والمجلد والنوع والحجم والمفتاح ومستوى الرؤية. ويكتب تدقيق الحذف في المرحلة A (عند اتخاذ القرار) وليس C.

### 6.5 المطابقة واكتشاف الانحراف (Reconciliation)

فحص أسبوعي تلقائي أو يدوي لمقارنة كائنات R2 مع صفوف الداتابيز لتحديد الكائنات اليتيمة والصفوف المعلقة ورفع تقرير بها (للقراءة فقط في المرحلة 1).

## 10. المراحل وترتيب التنفيذ

### المرحلة 0 — إصلاحات حيادية السلوك (Phase 0)

4. تنظيف وحذف المفاتيح التي نجح رفعها فقط عند حدوث أخطاء.
5. توسيع `isForeignKeyViolation` ليتعرف على رمز الخطأ 23001.

### المرحلة 1 — الواجهة الخلفية (Phase 1: Backend)

1. ملف الترحيل: إنشاء الأنواع Enums؛ جدول `folders`؛ تعديلات جدول `files` (تحويل الحالة، الاسم، النوع، الحجم إلى bigint)؛ المفاتيح الأجنبية المركبة والقيود؛ حذف الحقول القديمة؛ إضافة `media` لأسماء الصفحات وصلاحيات أدوار النظام.
2. تحديث ثوابت الصفحات والصلاحيات وقواعد متغيرات البيئة.
3. تحديث عميل R2، وبناء وحدات `lib/media/*`، وتحديث الفحص الدوري ليعتمد على `retryDeleting`، وإضافة `claimFiles`.
4. بناء معالجات المسارات في `app/api/dash/media/*`، وملف الرسائل العربي، وإعادة تسمية مسار رفع النماذج إلى `/api/upload/file`.
5. تحديث محاكي التخزين، كتابة اختبارات الوحدة والتكامل، وإعادة توليد مواصفات OpenAPI.
6. تقرير مطابقة البيانات الأسبوعي.

### المرحلة 2 — واجهة المستخدم (Phase 2: Frontend)

إصلاح المتطلبات المسبقة، ثم بناء صفحة الوسائط ومكون الاختيار؛ وإضافة جدول أمثلة تجريبي بسيط `demo_assets` في الباك إند (يحتوي على عمود مباشر وجدول وسيط، ويبقى خلف مسارات التطوير فقط dev-only ما لم يرغب المالك بتثبيته).

### اعتماد آلة حالات الحذف (State Machine) للمراجع الثاني:

تم قبول جوهر الفكرة (استخدام علامة `deleting` وتنفيذ اتصال R2 خارج معاملات قاعدة البيانات، وجعل الفحص الدوري الليلي هو أداة إعادة المحاولة) احتراماً لقاعدة المشروع الصارمة بعدم فتح معاملات عبر الشبكة. مع إغلاق ثغرة التوقيت (TOCTOU) عبر المفتاح الأجنبي المركب الذي يمنع ربط أي كيان بملف في حالة الحذف، وبدون الحاجة لإدخال بنية طوابير معقدة لا وجود لها في المشروع.

### النقاط المرفوضة وأسبابها:

- **الإبقاء على العقد القديم لـ `/api/upload/image`:** لا يوجد مستهلك فعلي يعمل حالياً، وتم تصحيح المسار لـ `/api/upload/file`.
- **الرسائل بالإنجليزية:** كل رسائل الواجهة في المشروع بالعربية، وتم تأكيد ذلك مع المالك.
- **تأجيل حذف الدفعات:** يشارك الحذف الفردي نفس المسار والكود وهو آمن ويعيد المحاولة ذاتياً.
- **حصر الإصدار الأول بالصور فقط:** المالك طلب دعم الـ PDF، وسيشحن مع فحص توقيع رقمي وميزانية حجم خاصة وبترويسة تنزيل للحماية.
