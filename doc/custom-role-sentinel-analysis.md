# لماذا نرسل `"custom"` بدل رقم في `roleId`؟

## السؤال

في الـ APIs الخاصة بالمستخدمين، نرى أنَّ `roleId` أحياناً يكون رقماً حقيقياً (FK يشير إلى صف في جدول `roles`)، وأحياناً يكون النص `"custom"`.

السؤال الطبيعي:
> طالما أنَّ الجدول فيه عمود `scope` يُحدِّد نوع الدور (`system` / `standard` / `custom`)، لماذا نعبث بقيمة `roleId` ونجعلها تحمل معنيين؟

## الخلفية: كيف يعمل النظام الآن

### في قاعدة البيانات
- جدول `roles` فيه عمود `scope` يأخذ إحدى ثلاث قيم: `system`, `standard`, `custom`.
- جدول `users` فيه عمود `role_id` وهو **دائماً رقم حقيقي** يشير إلى صف في `roles`. لا يُحفظ فيه أبداً النص `"custom"`.
- الدور المخصص في DB = صف عادي في `roles` لكنَّ `scope` فيه يساوي `custom`، واسمه يبدأ بـ `custom-` (مثل `custom-0194f3...`).

### في الـ API
- **عند الإرسال من العميل**: لو المستخدم اختار دوراً جاهزاً، يُرسل `roleId: 5`. لو اختار "مخصص"، يُرسل `roleId: "custom"` مع مصفوفة `permissions`.
- **عند الاستقبال من العميل**: لو `roleId === "custom"`، ينشئ الـ API دوراً جديداً في `roles` بـ `scope='custom'` ويستخدم الـ ID الناتج.
- **عند الإرجاع للعميل**: لو الدور المرتبط بالمستخدم `scope === 'custom'`، يُرجع الـ API `roleId: "custom"` بدل الرقم الحقيقي.

إذاً `"custom"` هو مجرد **كلمة سر** متفق عليها بين العميل والـ API، ولا علاقة لها بقاعدة البيانات.

## السؤال يبقى: لماذا هذا التعقيد؟

هناك ثلاثة أسباب. اثنان منها قويَّان والثالث قابل للنقاش.

### السبب الأول: عند الإنشاء، لا يوجد ID بعد

تخيَّل أنَّ المستخدم يملأ فورم إنشاء حساب جديد ويختار "دور مخصص" مع صلاحيات معيَّنة.

في هذه اللحظة:
- صف الدور في جدول `roles` **لم يُنشأ بعد**.
- العميل ليس لديه ID ليرسله.

فكيف يقول العميل للـ API "أنشئ دوراً جديداً بهذه الصلاحيات"؟ يحتاج إشارة.

الحل الحالي: يرسل `roleId: "custom"` + مصفوفة `permissions`. الـ API يفهم أنَّ عليه إنشاء الدور أولاً.

هذا السبب **قويٌّ جداً** ولا علاقة له بنوع الـ ID (رقم أو UUID) — المشكلة هي نفسها في الحالتين.

### السبب الثاني: تبسيط الـ dropdown في الواجهة

الفورم في [components/users/form/role.tsx](../components/users/form/role.tsx) يعرض قائمة منسدلة فيها:
- الأدوار الجاهزة (admin, editor, …)
- خيار ثابت اسمه "مخصص"

كل عنصر في القائمة له `value` تُستخدم للمقارنة `selectedValue === role.value`.

**لو أرجع الـ API الـ ID الحقيقي للدور المخصص** (مثلاً `42`)، فالعميل يحتاج عند تحميل بيانات مستخدم موجود أن:
1. يرى أنَّ `roleId = 42`.
2. يبحث عن صف الدور ويفحص `scope === 'custom'`.
3. يُحوِّل القيمة إلى `"custom"` لتطابق خيار "مخصص" في الـ dropdown.

**مع الحل الحالي**، الـ API يُرجع مباشرة `roleId: "custom"`، والفورم يُطابقها مع خيار "مخصص" بدون أيِّ منطق إضافي.

هذا السبب **قوي عملياً** — يُبسِّط كل صفحة فيها هذا الـ dropdown.

### السبب الثالث: الدور المخصص ليس "كياناً عاماً"

هنا نقطة دقيقة تستحق التوضيح.

الأدوار الجاهزة (`scope='standard'`) مثل "admin":
- تظهر في صفحة إدارة الصلاحيات.
- يُمكن تعيينها لعدة مستخدمين.
- لها هويَّة مستقلة وقابلة للإشارة إليها بالـ ID.

الأدوار المخصصة (`scope='custom'`):
- لا تظهر في أيِّ قائمة عامة.
- مرتبطة بمستخدم واحد فقط (علاقة 1:1).
- تُحذف تلقائياً عند تغيير دور المستخدم أو حذفه (انظر [app/api/dash/users/\[id\]/route.ts:431-451](../app/api/dash/users/[id]/route.ts#L431-L451)).

لذلك **الدور المخصص ليس له "هوية" يحتاج العميل أن يعرفها**. ما يهم العميل هو: هل هذا المستخدم لديه دور مخصص؟ وما هي صلاحياته؟

إرجاع `roleId: "custom"` + `permissions[]` يعبّر عن هذه الحقيقة بشكل دقيق. إرجاع `roleId: 42` للعميل يُوهمه بوجود كيان اسمه "الدور رقم 42" مع أنَّه في الواقع جزء غير منفصل من ذلك المستخدم.

> **ملاحظة**: في نسخة سابقة قلت إنَّ "إظهار UUID يُسرِّب تفاصيل تنفيذ". هذا الكلام غير دقيق لأنَّ:
> - هذا المشروع يستخدم أرقاماً متسلسلة (`integer`) وليست UUIDs — انظر [db/schema.ts:119](../db/schema.ts#L119).
> - الكود المعلَّق في [db/schema.ts:109-112](../db/schema.ts#L109-L112) يُظهر أنَّ المشروع قابل للتبديل بين الاثنين.
> - نوع `EntityID` يُجرِّد الاختلاف.
>
> إذاً الحُجَّة الحقيقية ليست "إخفاء شكل الـ ID"، بل "الدور المخصص ليس كياناً قابلاً للإشارة".

## ثمن هذا التصميم

الحل الحالي ليس مجانياً. هناك ثلاث تكاليف واضحة:

### 1. تلوث في الأنواع
في كلِّ مكان فيه `roleId`، النوع صار:
```ts
EntityID | "custom" | null
```
انظر [types/user.ts:18](../types/user.ts#L18). هذا الاتحاد (union) ينتشر في كلِّ الأنواع المتعلِّقة بالمستخدم والفورم.

### 2. منطق "قناع" متكرِّر في الـ API
في كلِّ مكان يُرجع بيانات مستخدم، تُكتب نفس السطر:
```ts
roleId: role?.scope === CUSTOM_ROLE_VALUE ? CUSTOM_ROLE_VALUE : u.roleId
```
موجود في:
- [app/api/dash/users/route.ts:111](../app/api/dash/users/route.ts#L111)
- [app/api/dash/users/\[id\]/route.ts:194-197](../app/api/dash/users/[id]/route.ts#L194-L197)

لو أُضيف endpoint جديد يُرجع مستخدماً، لازم يُكرِّر نفس المنطق.

### 3. غموض دلالي
حقل `roleId` في طبقة الـ API يحمل معنيين مختلفين:
- معنى "مؤشر إلى دور موجود" (FK)
- معنى "أمر بإنشاء دور جديد" (`"custom"`)

هذا الخلط يجعل فهم الكود أصعب على المطوِّرين الجدد.

## بدائل أنظف لو أُعيد التصميم

### البديل 1: حقل منفصل للنيَّة (الأنظف)
```ts
{
  roleId: EntityID | null,
  customPermissions?: Permission[]  // وجوده = نيَّة إنشاء دور مخصص
}
```
- `roleId` يبقى نوعاً نقياً (رقم فقط).
- النيَّة مُعبَّر عنها بحقل منفصل.
- لا يحتاج قناع عند الإرجاع.

### البديل 2: discriminated union
```ts
type RoleAssignment =
  | { type: "standard"; roleId: EntityID }
  | { type: "custom"; permissions: Permission[] }
```
- أوضح تماماً في التعبير.
- لكنَّه يُجبِر على إعادة تصميم الفورم.

### البديل 3: إضافة `scope` إلى الـ DTO
```ts
{ roleId: EntityID, scope: "standard" | "custom" }
```
- العميل يتعامل مع الاثنين معاً.
- ما زال يحتاج تحويل في الـ dropdown، لكنَّه أوضح.

## الخلاصة

- التصميم الحالي **مبرَّر ومنطقي**، خصوصاً من ناحية تبسيط الفورم ومشكلة "لا ID عند الإنشاء".
- لكنَّه يدفع ثمناً حقيقياً في نظافة الأنواع وتكرار منطق القناع.
- **البديل 1** (حقل `customPermissions` منفصل) هو الأنظف لو أُعيد التصميم من الصفر.
- التحويل الآن يمسُّ الأنواع والفورم وعدَّة endpoints — تكلفة التحويل أكبر من المكسب الجمالي.

**التوصية**: الإبقاء على التصميم الحالي، مع توثيق هذا القرار (هذا الملف) حتَّى لا يتساءل المطوِّرون لاحقاً.
